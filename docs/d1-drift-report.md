# D1 ↔ worker drift report

> Last verified 2026-07-25 (snapshots re-pulled and confirmed unchanged).
> Generated by comparing every `FROM` / `JOIN` / `INSERT INTO` /
> `UPDATE` in `workers/*/src` against `workers/*/schema.sql`, which is itself
> generated from the **live** Cloudflare D1 databases. D1 is final: code
> follows the database, not the reverse.

## Re-running the audit

`workers/*/schema.sql` is now a faithful dump of each live database, so the
check is local — no Cloudflare round-trip needed. Extract the table names a
worker's SQL touches and subtract the `CREATE TABLE` / `CREATE VIEW` names in
its snapshot. Regenerate a snapshot after applying migrations with:

```sql
SELECT type, name, sql FROM sqlite_master
WHERE sql IS NOT NULL AND name NOT LIKE 'sqlite_%' AND name <> 'd1_migrations'
ORDER BY CASE type WHEN 'table' THEN 0 WHEN 'view' THEN 1 ELSE 2 END, name;
```

Snapshots exclude `d1_migrations` (wrangler's ledger), `_cf_KV`, and FTS5
shadow tables, which their virtual tables recreate automatically.

# Duplication audit

> Added 2026-07-25 after re-pulling all eight schemas. The regenerated files
> came back byte-identical to the committed ones, so the snapshots below are
> confirmed current rather than assumed current.

Method: compare every table's column set within each database and across all
eight, ignoring structural columns (`id`, `created_at`, `status`, …) that carry
no meaning. Candidates were then checked against live row counts and against
what actually reads them. Only findings that survived that check are listed.

## Real duplication

### 1. `cyb_*_band` — six tables, one shape (km_core)

`cyb_root_band` (28 rows), `cyb_ss_band` (12), `cyb_ps_band` (19),
`cyb_wv_band` (6), `cyb_doc_band` (6) share an identical 24-column core;
`cyb_wv_band` adds `wv_domain_slug`, `cyb_ps_band` adds `layer_key`, and
`cyb_doc_band` omits the study/card/retention columns because documents are
built but never studied. A sixth, `cyb_pt_band`, is a reduced shape.

The table *identity* is the discriminator. `v_cyb_binding_broken` recovers a
band's "family" by probing all six in a `CASE` and writing the result into a
binding UID (`BIND:root:…`, `BIND:ss:…`) — so the track is already a
first-class value in the data, just not a column. One `cyb_band` table with a
`track` column would replace the family and that `CASE`.

**Do not consolidate without a plan.** No worker code touches these, but they
are not dead: they are read by Claude skills querying D1 directly
(`kmaps-root-card/QUERIES.sql` selects from `cyb_root_band` twice) and by nine
`cyb_*_build` / `_board` / `_content` views. `cyb_root_band` is also a *mirror*
of `km_arabic_linguistic.ar_ling_reg_sub_layer` — that is what `synced_at` is
for — so it is deliberate cross-database denormalisation, not an accident.

### 2. `core_podcasts` / `core_podcast_participants` / `core_talking_points`

Superseded by the studio domain (`st_episodes`, `st_participants`,
`st_talking_points`). The core copies hold **0 rows**; studio holds 8 episodes,
5 participants, 48 talking points. `core/src/repositories/podcast.repo.ts` is
imported by nothing and the deployed core worker never queries them.

Column overlap with the `st_*` tables is **zero**, so this is not a copied
schema — it is an earlier, abandoned design of the same concept. Safe to drop
along with `podcast.repo.ts` and `podcast.schema.ts`.

### 3. Code duplication: the two book-display route files

`routes/iraab-display.ts` and `routes/tafsir-display.ts` carry byte-identical
`parseArr` / `parseObj` / `parseOrNull` helpers, the same five-step pipeline
and the same group-resolution algorithm. Extractable into a shared module.

Related gap: `iraab-display.ts` hardcodes `links: []` and never queries
`qr_irab_book_display_link`. Both link tables are currently empty, so nothing
is lost today, but the read path does not exist.

## Ruled out — looks duplicated, is not

| Candidate | Why it is not duplication |
|---|---|
| `qr_irab_book_display_*` vs `qr_tafsir_book_display_*` | Deliberate and documented. `database/migrations/km-quran/012_tafsir_display_layer.sql` states an architecture rule keeping the row populations disjoint (1,526 legacy iʿrāb rows were deleted from the tafsir side to enforce it). Tafsir carries a scholar/chronology dimension iʿrāb lacks; the `block_type` enums share no values. ~690k rows across the two families. |
| ~180 FTS pairs scoring 1.00 | All fts5 tables share a shape; each indexes a different base table. |
| `ar_ling_concept_block` vs `ar_ling_lexicon_block` | Disjoint parent FKs — grammatical terms vs dictionary roots — so they could not merge without a polymorphic parent. 5 rows vs 1,013,624. The real issue is separate: `ar_ling_concept_block` has zero readers and zero writers anywhere, and no migration in this repo creates it. |
| `wv_vice_profiles` / `wv_virtue_profiles` | Deliberate opposites (8 and 10 rows). |
| `wv_source_units` / `wv_source_units_trash` | Soft-delete archive (73 / 19 rows). |
| `qr_passage_analysis` / `qr_surah_analysis` | Different scopes (13 / 1 rows). |
| `qr_src_code` / `ar_ling_src_code`, `*_source_chunk`, `*_claim_evidence_link` | Cross-database copies are required: D1 cannot join across databases, so per-domain lookup tables are the architecture working as intended. |

## Other results

- **No rename leftovers.** All 568 tables were checked for singular/plural
  twins surviving together. None.
- **205 of 568 tables (36%) are referenced by no worker code.** That is not the
  same as dead — the `cyb_*` family and much of the AL build layer are written
  by scripts and skills. It is the pool to search, not a delete list.
- **`docs/architecture/multi-db-topology.md` is out of date.** It describes
  km_core as "24 tables … No domain-specific tables"; live km_core has 67
  tables including 29 `cyb_*` ones that are domain-specific. Worth reconciling.

## Fixed in this pass

- **Three unreachable routes.** `shared/src/router.ts` returns the first match
  in registration order and `:id` matches any segment, so a literal path
  registered *after* `:id` on the same prefix was dead, silently 404-ing:
  `/al/morphology/paradigms`, `/ar/exercises/sample`, `/ar/vocabulary/due`.
  All three now register before their `:id` sibling.
- **`/al/expressions` threw at D1.** Both endpoints selected
  `expression_type`, `gloss_en` and `notes` from `ar_ling_root_lemma_tabir`;
  the real columns are `expression_en`, `notes_md` and a foreign key
  `expression_type_id` into `ar_ling_root_lemma_tabir_kind`. Rewritten with a
  join so `?type=` still filters on the human `type_key`, verified against
  live data. The response shape is unchanged.

Note this class of bug — table exists, columns do not — is invisible to the
audit above, which only checks table names. A column-level check would catch
more of it.
